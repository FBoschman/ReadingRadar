# P5 - UX and accessibility researcher

Owns: keyboard, semantics, focus, contrast, mobile, error prevention. Ran T09 and T10 by cognitive
walkthrough of the markup and the script, because there is no live browser in this environment. Every
finding below is marked with how it was obtained.

## Verdict

The page is well built for a reader with a mouse and normal sight: the tab bar is real buttons, every
input has a label, the tables have headers, the print sheet exists, and the layout is responsive by
grid. Two things break that. **The item list is a set of clickable `div` elements, so it cannot be
reached by keyboard at all** (T09 fails at the first step: there is no focusable element in the list).
And **the radar is not published anywhere**, so the Monday review cannot happen on a phone (T10 fails
before it starts). Both are cheap to repair, and both are the kind of thing that quietly excludes a
reader who is tired, on a train, or using a screen reader.

## Findings

| # | Sev | Feature | Finding | Evidence | Fix |
|---|---|---|---|---|---|
| 1 | S1 | F04 | The 162 item rows are `div` elements with a click handler. `tabindex` appears 0 times and `keydown` 0 times in `index.html`, so the list is unreachable and unopenable by keyboard. | `grep` over `index.html`: `tabindex` 0, `keydown` 0, `data-action` 7, `<button` 8 (all outside the list). Cognitive walkthrough, T09. | Give each row `role="button" tabindex="0"`, handle Enter and Space, and add a visible focus ring. |
| 2 | S1 | F01 | The radar is not published, so T10 cannot start. | `https://fboschman.github.io/ReadingRadar/` returns 404; the Pages API returns 404. | Publish on GitHub Pages from `main` and `/`; the app is already a static file. |
| 3 | S2 | F04 | The item row is announced as a group of text, not as a control, and the selected row is marked by a colour shadow only. | `renderItemList` builds `<div class="item" data-action="open-item">` with a class change for `sel`. Needs a human eye for the shadow. | Give the row a role, an `aria-pressed` or a real button, and a state that is not only a shadow. |
| 4 | S2 | F24 | When a filter changes the count, nothing announces it. A screen-reader user hears no feedback after typing in the search box. | `#itemCount` is a plain span with no live region. | Add `aria-live="polite"` to the count. |
| 5 | S3 | F08 | There is no explicit focus style, so keyboard focus depends on the browser default and on the OS. | No `:focus` or `:focus-visible` rule in the stylesheet. Needs a human eye. | Add a two-pixel focus ring with a contrast of at least 3 to 1 against both backgrounds. |
| 6 | S3 | F09 | The abstract would be a long text block in a two-column grid; on a phone that becomes a very long scroll with the metadata above it. | The detail panel is `grid side`; no collapse control exists. | Put the abstract behind a disclosure on narrow screens. |

## What would change my mind

Findings 1 and 2 are the gate for me. A keyboard user cannot use this instrument at all today, and a
phone user cannot open it. Both fixes are small: about ten lines of markup and twenty seconds of a
settings change. I would also insist on the focus ring, because a keyboard path with no visible focus
is only half a path.
