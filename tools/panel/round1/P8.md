# P8 - Maintenance engineer

Owns: unattended operation for a year, and how the thing fails. Ran T08 and T11.

## Verdict

For a personal instrument this is a good build. It has no secrets, no server, no database, one
dependency (Python 3.14), a validator before every commit, a generated bundle, a log, and a scheduled
task that ran end to end on the first try and pushed its own commit. The failure modes are named in
`BLOCKERS.md`, which is rarer than it sounds. Two operational weaknesses remain, and both will bite
within a year. **Nothing prunes the queue**: 213 candidates today, growing by 30 to 210 a week, with no
cap and no expiry, so in six months the bundle, the queue and the reader's attention all degrade. And
**there is no failure alarm**: if the task does not run, the radar is silent, and the only trace is the
age of the data on a page someone has to open. An unattended instrument that stops without saying so is
the classic way a personal tool dies.

## Findings

| # | Sev | Feature | Finding | Evidence | Fix |
|---|---|---|---|---|---|
| 1 | S1 | F15 | If the weekly task fails, nothing tells the reader. The last run stays in `lastRun.json` and the app shows its age, but nobody opens the app to find out that it did not run. | T11 walkthrough: the age chip is the only signal; `run-weekly.ps1` exits non-zero but the Task Scheduler result is invisible to the reader. Log: `logs/weekly-2026-10-12.log`. | Have the task write a one-line status file and, on failure, put a visible banner in the app; optionally send a message if a channel exists. |
| 2 | S1 | F23 | Nothing bounds the queue. It grew from 0 to 213 in one day, and no run prunes it. The bundle carries a number, so the growth is invisible in the app. | `data/inbox/items/` holds 213 files; the harvest adds candidates each run; no expiry exists in `weekly.py` or `harvest.py`. | Add an expiry rule: drop an unjudged candidate after 4 runs, or when its id is older than 30 days, and record what was dropped. |
| 3 | S2 | F25 | The task pushes to a public repository unattended. The validator protects the schema, not the content, so a bad run is published before anyone reads it. | `weekly.py` calls `git commit` then `git push`; the validator runs before both. | Push to a branch by default and let a human merge, or keep the push and accept the risk in writing. |
| 4 | S2 | F25 | The task runs only when the user is logged on, with "start when available". A laptop that is shut for a week loses those runs entirely: there is no catch-up of the window. | `install-task.ps1` uses the interactive principal; the trigger has `StartWhenAvailable`. | On a missed week, widen the window automatically: use the gap between the last run date and today, capped at 14 days. |
| 5 | S3 | F25 | The log grows without rotation and is written with a fixed name per day. | `logs/weekly-YYYY-MM-DD.log`. | Keep 90 days, or rotate at 1 MB. |
| 6 | S3 | F25 | The vault path, the mail address and the thesis of the polite pool are hard-coded, so the kit is bound to this machine and this reader. | `radar_lib.py` holds `MAILTO`; `profile.json` holds an absolute vault path. | Move both into the profile as configuration, and fail with a clear message when they are missing. |
| 7 | S3 | F14 | A source that fails is recorded, but the record is one run deep, so a streak (Crossref down for three weeks) looks like a single event. | `lastRun.json` is replaced each run. | Keep the append-only source history (the same fix as P3 finding 4). |

## What would change my mind

Findings 1 and 2 are the ones I would not sign off without. A staleness banner plus a queue expiry rule
are perhaps twenty lines together, and they are the difference between a tool that survives a year and
one that quietly rots. I would accept the unattended push (finding 3) only with the risk written into
`RUNBOOK.md`, because the alternative adds a step the reader will skip.
